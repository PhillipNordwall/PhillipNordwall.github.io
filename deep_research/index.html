A field guide to evidence you can audit

One question.
Many perspectives.
Evidence under scrutiny.

The harness sends one research question to several agent CLIs (agy, codex, claude). They research it independently, review each other's reports without knowing who wrote them, reassess with every review in hand, and each writes a final synthesis. Each step is committed to git, and the ledger records which framework and model produced each artifact. Models never see that information.

Why it's built this way

Independence

Each session is a new, non-interactive process without conversation continuity. This reduces carryover bias; writing style can still suggest authorship.

Blindness

Artifacts get random IDs. Agents work in throwaway folders outside the repo. Phrases where an agent names itself, its tools or its connectors are redacted.

Provenance

A SQLite ledger records the framework, version, model and where the model name came from, plus effort, timings, token usage and session IDs. Run dr reveal to rebuild the mapping without involving a model.

Resumable

Progress is committed after every session. Re-running skips finished sessions and retries failed ones. Each phase waits for the one before it.

The method · phase by phase

From question to defensible answer

Each stage has a different job. Select a phase to inspect its inputs, outputs, purpose and working contract.

Phase 00

Intake

Define the decision before gathering evidence.

A precise question keeps reviewers focused on the same audience, timeframe and decision. Scope reduces irrelevant research and makes coverage gaps assessable.

Reads

Your question and optional scope notes.

Produces

QUESTION.md, run.json, INDEX.md and a ledger run record.

What good work looks like

  • State what decision this research should support.
  • Specify audience, geography, timeframe and exclusions.
  • Import outside research now or before reassessment begins.
No agent session. The harness records intake and commits it when commits are enabled.
Read the evaluation criteria and prompt contracts →
Phase 01

Research

Build independent evidence bases.

Independent searches can uncover different sources and counterarguments. Shared mistakes can still occur, so later phases must check whether sources are truly independent.

Reads

The question and scope only; no other reports.

Produces

01-research/R-*/report.md; one report per agent.

What good work looks like

  • Decompose into 3–8 sub-questions.
  • Seek two independent sources for important claims, or mark single-source.
  • Search for counter-evidence; label facts, consensus, contested claims and inference.
N fresh sessions. Each report has eight required sections and numbered findings F1, F2, …
Read the evaluation criteria and prompt contracts →
Phase 02

Blind review

Test the claims against their sources.

An articulate report can cite real sources that do not support its claims. Blind review makes evidence and reasoning the basis for criticism and includes independent self-review.

Reads

The question and exactly one anonymous report per session.

Produces

02-review/V-*/review.md; a separate review for each agent × reviewed report.

What good work looks like

  • Verify at least 8 load-bearing claims, or all if fewer.
  • Independently spot-check at least 3 key claims.
  • Score seven dimensions, identify specific errors and assign a disposition to every finding.
N × (N + K) sessions, where K is the number of imported reports eligible for review. Imports with --no-review remain in later phases.
Read the evaluation criteria and prompt contracts →
Phase 03

Reassessment

Adjudicate disagreements on evidence.

Reviewers can be wrong. Reassessment separates refuted claims from unverified ones and examines common sources, conflicting verdicts and collective blind spots.

Reads

All completed reports and reviews, grouped by report in a manifest.

Produces

03-reassessment/A-*/reassess_<R-id>.md for every report, plus overview.md.

What good work looks like

  • Read every report and review.
  • Re-check important disputed claims yourself.
  • Rule on every finding and revise confidence; compare reliability across reports.
N sessions. Five finding rulings and a comparative reliability score of 1–5. Do not average reviewer opinions.
Read the evaluation criteria and prompt contracts →
Phase 04

Synthesis

Write a coherent, traceable answer.

Organizing by theme turns the evidence into a useful answer while retaining its uncertainty and audit trail. There are N final syntheses, rather than one automatically chosen winner.

Reads

All reassessments as primary input, plus original reports for citations and nuance.

Produces

04-synthesis/S-*/synthesis.md; one final report per agent.

What good work looks like

  • Merge duplicate findings and use a unified bibliography.
  • Resolve conflicting adjudications with reasoning and evidence.
  • Keep unresolved questions, refuted claims and R-/A- provenance visible.
N sessions. Ten required sections, final High/Medium/Low confidence, and a machine-readable summary.

What happens when a session fails?

A nonzero CLI exit or a CLI-reported error fails the task even if it wrote a long response or output file. Missing or undersized deliverables also fail. The harness records provenance and logs; rerunning skips completed tasks and retries failures up to max_attempts.

bin/dr run <run-id>
# Retry even after the attempt limit:
bin/dr run <run-id> --retry-failed
# Continue past an incomplete phase with at least two successful inputs:
bin/dr run <run-id> --allow-partial

Partial runs can have incomplete evidence. Later completed tasks are skipped on resume; use a new run for a fresh, comprehensive pipeline after changing the evidence base.

Quality controls · inspect the contract

How the work is evaluated

These criteria come from the repository’s phase prompts. Expand any contract below to inspect the complete prompt, including the required report sections and JSON summaries. Everything is embedded in this file and available offline.

A rubric guides judgment. Reviews score each dimension and Overall from 1–5, with a one-line justification. The prompts do not define numeric anchors or weights. The harness checks process success and deliverable existence/size; it does not automatically validate scores, JSON schemas, citations or research quality.

The seven review dimensions

DimensionWhat the reviewer examinesScale
Factual accuracyAre the claims correct under verification?1–5 + justification
Citation fidelityDo the cited sources say what the report claims?1–5 + justification
Source qualityAre the sources primary, reputable and current?1–5 + justification
Coverage / completenessDoes the report answer the actual question across relevant perspectives?1–5 + justification
Reasoning & calibration of confidenceDoes the reasoning hold, and does confidence match the evidence?1–5 + justification
Treatment of counter-evidenceDoes the report engage with strong competing evidence?1–5 + justification
Clarity & traceabilityCan a reader locate claims, sources, methods and limitations?1–5 + justification

From criticism to a final ruling

Review · disposition

What should happen to a finding?

Accept · Accept with caveat · Revise · Reject · Unverifiable

Errors are ranked Critical / Major / Minor. Each criticism points to a finding, section or short quote and supplies evidence where possible.

Reassessment · ruling

What survives scrutiny?

Confirmed · Confirmed-with-caveat · Revised · Refuted · Unresolved

Record revised confidence and the basis for each ruling. The overview compares report reliability on a 1–5 scale with justification.

Synthesis · confidence

How much trust is warranted?

High · Medium · Low

Use independent corroboration and performance under review. Keep unresolved conflicts visible. Do not reinstate refuted claims without new evidence.

# Task: Independent Deep Research

You are a senior research analyst producing an **independent, evidence-based deep
research report** on the question below. Several other analysts are researching the
same question on their own, and their reports will later be cross-reviewed. What
makes yours valuable is depth, accuracy, and sourcing you can trace, not length.

## Research question
{{QUESTION}}

## Scope / context notes
{{SCOPE}}

(The same text is in `inputs/question.md`.)

## Method (do all of these)
1. **Decompose** the question into 3–8 sub-questions. Write them down before
   researching. Identify which ones are factual, which are interpretive, and which
   are predictive.
2. **Search broadly, then deeply.** Use web search/fetch extensively. Prefer primary
   sources (papers, official docs, filings, datasets, standards, direct statements)
   over secondary coverage. For anything important, find **at least two independent
   sources**, or label it single-source.
3. **Seek disconfirming evidence.** For each major finding, actively search for
   counter-evidence, criticism, failed replications, or competing explanations.
4. **Check recency.** Note publication dates. Flag where the evidence may be stale
   or the situation is changing fast.
5. **Separate** established facts, expert consensus, contested claims, and your own
   inference, and label each one.
6. **Quantify** where possible, with units, dates, and the source of each number.

## Deliverables
- `output/report.md`: the report, using **exactly** these top-level sections in
  this order:

```
# Research Report
## 1. Executive Summary            (5–10 bullet answer to the question, each with a confidence tag)
## 2. Sub-questions                 (the decomposition from step 1)
## 3. Key Findings                  (numbered F1, F2, … ; each: claim · evidence · sources [S#] · confidence High/Medium/Low · type Fact/Consensus/Contested/Inference)
## 4. Detailed Analysis             (narrative, organized by sub-question)
## 5. Counter-evidence & Contested Points
## 6. Gaps, Limitations & Open Questions
## 7. Methodology & Search Log      (what you searched, what you fetched, what failed or was paywalled)
## 8. Sources                       (numbered [S1]…; title, publisher/author, date, URL, accessed {{DATE}}, one-line note on reliability)
```

Every non-trivial claim in sections 1, 3 and 4 must cite `[S#]` or be explicitly
labelled *Inference* or *Unsourced*.

# Task: Independent Blind Review of a Deep Research Report

You are an **independent expert reviewer and fact-checker**. You've been handed
**one** deep research report written by an unknown analyst in answer to the
question below. Your review will be read alongside reviews by other independent
reviewers, and then used to decide which findings should be trusted. The process
depends on you being **rigorous, skeptical, specific, and fair**. A vague or
deferential review is a failed review. So is an unfairly harsh one.

## Research question
{{QUESTION}}

## Scope / context notes
{{SCOPE}}

## Input
- `inputs/question.md`: the question
- `inputs/report_{{SUBJECT_ID}}.md`: the report under review (ID `{{SUBJECT_ID}}`)

## Reviewer stance
- Assume nothing in the report is correct until you've checked it. Also assume
  nothing is wrong just because it's surprising.
- Evaluate the report **against the question**, not against the report you would
  have written. But do point out important things it missed.
- Don't guess who or what wrote the report. Authorship doesn't matter.
- Every criticism must point to a specific location (finding ID, section, or a
  short quote) and explain *why*, with evidence where possible.

## Required procedure
1. **Read the whole report** before judging it. Reports don't all follow the same
   template. If this one has no `F#` finding IDs, number its main findings yourself
   (F1, F2, … in order of appearance, each with a short quote) and use those IDs below.
2. **Verify citations.** Pick the report's **most load-bearing claims**: at least
   8 of them, or all of them if there are fewer, prioritizing the Executive Summary
   and the High-confidence findings. For each one, actually open the cited source
   (web fetch/search) and determine:
   - *Exists?* Does the source exist at that URL or under that title?
   - *Supports?* Does it actually say what is claimed: Supported / Partially /
     Not supported / Contradicted?
   - *Quality.* Primary or secondary? Reputable? Current?
   If you can't access a source, say so. Don't guess.
3. **Spot-check independently.** For at least 3 key claims, do your own quick search
   for corroborating or contradicting evidence that the report didn't cite.
4. **Audit the reasoning.** Look for logical leaps, correlation-vs-causation errors,
   cherry-picking, overgeneralization, base-rate neglect, confidence labels that
   don't match the evidence, internal contradictions, and stale data.
5. **Audit coverage.** Which sub-questions, perspectives, stakeholders, regions,
   timeframes, or major sources are missing? Which strongest counter-arguments go
   unaddressed?
6. **Check the form.** Are claims traceable? Are inference and fact clearly separated?
   Is the Methodology section honest about its limitations?

## Deliverable
- `output/review.md`, using **exactly** this structure:

~~~markdown
# Review of {{SUBJECT_ID}}
## 1. Summary Verdict
(3–6 sentences: overall reliability, the biggest strengths, the most serious problems.)

## 2. Scores (1–5, with one-line justification each)
| Dimension | Score | Justification |
|---|---|---|
| Factual accuracy | | |
| Citation fidelity (sources say what is claimed) | | |
| Source quality | | |
| Coverage / completeness vs the question | | |
| Reasoning & calibration of confidence | | |
| Treatment of counter-evidence | | |
| Clarity & traceability | | |
| **Overall** | | |

## 3. Claim Verification Table
| # | Report location | Claim (short) | Cited source | Source exists? | Supports claim? | Notes / evidence |
|---|---|---|---|---|---|---|

## 4. Independent Spot-checks
(Claim → what you searched → what you found → impact on the report's conclusion. Include URLs.)

## 5. Errors & Unsupported Claims
(Ranked by severity: Critical / Major / Minor. Each: location · problem · correction or evidence.)

## 6. Reasoning & Calibration Issues

## 7. Coverage Gaps & Missing Perspectives

## 8. Strongest Contributions
(The findings from this report that you judge most reliable and valuable, and why.)

## 9. Findings Disposition
| Finding | Disposition (Accept / Accept with caveat / Revise / Reject / Unverifiable) | Reason |
|---|---|---|
(Cover every F# in the report, or every finding you numbered.)

## 10. Recommendations to Improve

## 11. Machine-readable Summary
```json
{"subject": "{{SUBJECT_ID}}", "overall_score": 0, "scores": {"accuracy":0,"citation_fidelity":0,"source_quality":0,"coverage":0,"reasoning":0,"counter_evidence":0,"clarity":0},
 "claims_checked": 0, "claims_supported": 0, "claims_partial": 0, "claims_unsupported": 0, "claims_contradicted": 0, "sources_inaccessible": 0,
 "critical_errors": 0, "major_errors": 0, "minor_errors": 0,
 "dispositions": {"F1": "Accept"}}
```
~~~

# Task: Holistic Reassessment of Deep Research Reports in Light of Peer Review

You are a **senior research adjudicator**. Several analysts independently researched
the question below. Each report was then reviewed several times by independent blind
reviewers. You now have **all the reports and all the reviews**. Your job is to
reassess **each report** holistically: decide which of its findings survive scrutiny,
settle disagreements between reviewers, and recalibrate confidence.

## Research question
{{QUESTION}}

## Scope / context notes
{{SCOPE}}

## Inputs
- `inputs/question.md`
- `inputs/reports/<REPORT_ID>.md`: the original research reports
- `inputs/reviews/<REVIEW_ID>.md`: the reviews. Each one starts with a header naming
  the report it reviews.
- `inputs/MANIFEST.md`: which reviews belong to which report

{{INPUT_MANIFEST}}

## Stance
- Reviewers can be wrong too. Don't average opinions. **Adjudicate**: when reviewers
  disagree with each other or with the report, decide who's right on the evidence,
  and re-check the source yourself (web fetch/search) whenever the point matters.
- A claim isn't true just because several reports or reviewers repeat it. Check
  whether they rely on the same underlying source.
- Treat every report the same way. Don't guess authorship, and don't favor any
  report's style.
- Separate "the report is wrong" from "the report is unverified".
- Reports don't all follow the same template, and a report can have few or no
  reviews. Where a report has no `F#` IDs, use the IDs its reviewers assigned, or
  number its findings yourself. Where reviews are missing or thin, do the checking
  yourself, and say so in section 2.

## Procedure
1. Read every report and every review in full.
2. For each report, build a list of its findings and collect every reviewer's
   verdict on each one.
3. Where reviewers conflict, or a disposition is Revise/Reject/Unverifiable for an
   important finding, investigate it yourself and rule on it.
4. Look **across** reports. Corroboration from independent sources raises
   confidence. Contradictions between reports must be named and resolved, or
   explicitly left open.
5. Record anything important that **every** report missed.

## Deliverables
One file **per report**, plus one overview:

{{OUTPUTS}}

Each `reassess_<REPORT_ID>.md` must use this structure:

~~~markdown
# Reassessment of <REPORT_ID>
## 1. Reassessed Verdict            (reliability after all reviews; 3–6 sentences)
## 2. Reviewer Consensus & Disagreements  (where reviewers agreed, where they split, and your ruling with evidence)
## 3. Finding-by-Finding Reassessment
| Finding | Original confidence | Reviewer dispositions | Your ruling (Confirmed / Confirmed-with-caveat / Revised / Refuted / Unresolved) | Revised confidence | Basis (sources, checks you did) |
|---|---|---|---|---|---|
## 4. Corrections               (corrected statements for every Revised/Refuted finding, with sources)
## 5. Unique Contributions      (valuable findings that appear only in this report)
## 6. Residual Risks            (what still might be wrong and why)
## 7. Machine-readable Summary
```json
{"report": "<REPORT_ID>", "reassessed_overall": 0, "findings": {"F1": {"ruling": "Confirmed", "confidence": "High"}}}
```
~~~

`overview.md` must use this structure:

~~~markdown
# Cross-Report Overview
## 1. Comparative Reliability   (rank the reports with justification; scores 1–5)
## 2. Cross-Report Agreements   (findings corroborated by multiple reports, and whether the sources are truly independent)
## 3. Cross-Report Conflicts    (each conflict, the evidence, your ruling or "unresolved")
## 4. Collective Blind Spots    (what every report missed)
## 5. Quality of the Reviews    (were any reviews unreliable? where and why — judge content only)
~~~

Synthesis · evidence rules & ten sections

Source: prompts/synthesis.md

# Task: Synthesize a Final, Cohesive Deep Research Report

You are the **lead author** writing the definitive answer to the question below.
The evidence base comes from several independent research reports, each blind-reviewed
by multiple reviewers and then holistically reassessed by several independent
adjudicators. You have **all the reassessments** (your primary input) and the
**original reports** (for source details and nuance).

## Research question
{{QUESTION}}

## Scope / context notes
{{SCOPE}}

## Inputs
- `inputs/question.md`
- `inputs/reassessments/<REASSESSMENT_ID>/`: each holds `overview.md` and one
  `reassess_<REPORT_ID>.md` per report. **These are your primary input.**
- `inputs/reports/<REPORT_ID>.md`: the original reports, to recover sources, numbers
  and detail. Don't reinstate a claim the reassessments refuted unless you have
  new evidence.
- `inputs/MANIFEST.md`

{{INPUT_MANIFEST}}

## Rules for synthesis
- **Weigh the adjudications.** Where the reassessments agree, adopt their consensus.
  Where they disagree, compare their reasoning and evidence, re-verify the deciding
  sources yourself if needed (web fetch/search), and rule. Show your ruling.
- **Integrate. Don't concatenate.** Organize by sub-question or theme, not by
  source report. Merge duplicate findings and keep the best sources for each.
- **Calibrate.** Every finding gets a final confidence level (High/Medium/Low) based
  on independent corroboration and how well it held up under review.
- **Keep it traceable.** Cite original sources as `[S#]` in a unified bibliography.
  Also note which report and assessment IDs support each finding (e.g.
  `(R-1a2b3c4d F3; A-…)`) so the result can be audited.
- **Keep uncertainty visible.** Unresolved conflicts and collective blind spots must
  appear in the final report. Don't smooth them away.
- Original reports vary in structure. Cite their findings by the IDs the
  reassessments used.
- Don't guess the authorship of any input.

## Deliverable
- `output/synthesis.md`, with **exactly** these sections:

~~~markdown
# Synthesized Deep Research Report
## 1. Bottom Line                       (direct answer to the question in ≤ 200 words)
## 2. Executive Summary                 (bulleted, each with confidence)
## 3. Consolidated Findings             (numbered C1, C2, … ; claim · confidence · evidence · sources [S#] · provenance (R-/A- IDs))
## 4. Integrated Analysis               (narrative by sub-question/theme)
## 5. Resolved Disagreements            (what the inputs disagreed on and how you ruled, with evidence)
## 6. Unresolved Questions & Blind Spots
## 7. Refuted or Withdrawn Claims       (claims from the original reports that did not survive review, and why)
## 8. Confidence & Methodology Notes    (how evidence was weighed; limits of this synthesis)
## 9. Unified Bibliography              ([S1]…; title, author/publisher, date, URL)
## 10. Machine-readable Summary
```json
{"bottom_line": "", "findings": [{"id": "C1", "claim": "", "confidence": "High", "provenance": ["R-…"]}], "unresolved": [""]}
```
~~~

Common rules · anonymity, honesty & workspace

Source: prompts/_common.md

## Operating rules (apply to this whole task)

- **Workspace.** You are working in an isolated directory. Inputs are under `inputs/`.
  Write your deliverables **only** to the paths listed under *Deliverables*, inside `output/`.
  Do not modify `inputs/`. You don't need, and shouldn't look for, anything outside this directory.
- **Anonymity.** This is a blind, multi-party process. Do **not** state or hint at
  which AI model, vendor, product, or tool you are (no "As Claude…", "I'm Codex…",
  "Generated by Gemini…", signatures, or model IDs). Don't speculate about who wrote
  any input document. Judge every input only on its content. You can still mention
  companies or products when they're part of the research subject itself.
  When you describe your method, name tools only generically ("web search",
  "web fetch", "file reader"). Never name your agent, CLI, connectors, plugins,
  MCP servers, skills, or runtime environment.
- **Non-interactive.** No human is available to answer questions. Make reasonable,
  explicitly stated assumptions and keep going. Never stop to ask for confirmation.
- **Honesty over polish.** Say what you verified and what you didn't. Mark uncertainty.
  Never invent sources, quotes, statistics, URLs, or dates. If a tool or the web is
  unavailable, say so plainly in the deliverable rather than writing from memory as
  if it were sourced.
- **Today's date** is {{DATE}}. Treat recency accordingly.
- **Finish** by making sure every deliverable file exists and is complete, then reply
  with one line: `DONE: <comma-separated deliverable paths>`.

Quickstart

You need Python 3.11+ with nothing to install, the agent CLIs on your PATH and logged in, and this repo checked out.

  1. Check what each tool offers

    Lists each agent's configured model plus the models and thinking levels it can use. 
    bin/dr options

  2. Pick models and thinking levels

    Choose interactively, or set values directly. The edit keeps the comments in config.toml. 
    bin/dr config
# or non-interactively, committing the change:
bin/dr config --set codex.model=gpt-6.1-sol --set codex.effort=high --commit

  3. Check the plumbing cheaply

    Offline first (mock agents, no tokens), then the real CLIs on cheap models. 
    python3 -m unittest discover -s tests -p 'test_*.py'
tests/offline.sh
tests/smoke.sh research,review

  4. Record your question (intake)

    bin/dr new "What is the current evidence on X for Y?" \
  --scope "Audience: engineering leads. Timeframe: 2023-present. Exclude vendor marketing."
    This prints the run ID, for example 2026-11-04-what-is-the-current-evidence-on-x.

  5. Optional: add research done elsewhere

    Reports from another tool or done offline join as anonymous R- reports. They're reviewed, reassessed and synthesized with the rest, and add no agent sessions of their own. Import before reassessment starts. 
    bin/dr import <run-id> offline-report.md --label vendor-deep-research
# skip peer review, but still reassess + synthesize it:
bin/dr import <run-id> notes.md --no-review
# or at intake:
bin/dr new "question" --import offline-report.md

  6. Choose a queued question

    Repeat intake for each question you want to save. This command lists them oldest first. Importing background research leaves a question queued. 
    bin/dr queue

  7. Start the question you picked

    Use any ID from the queue. Once a phase dispatches agent work, find the question with bin/dr list and resume it with the same ID. A full run is 3N + N² sessions (18 with three agents), plus N reviews for each imported report, and can take hours. Run it detached. 
    nohup bin/dr run <run-id> > run.log 2>&1 &
bin/dr status <run-id> --blind

  8. Read and reveal

    Start with runs/<run-id>/INDEX.md, then the 04-synthesis reports. Reveal the mapping only after you've read them. 
    bin/dr reveal <run-id>
bin/dr reveal <run-id> --out mapping.json
If a session fails, run bin/dr run <run-id> again. Finished work is kept. To continue past an incomplete phase, add --allow-partial; at least two artifacts from the preceding phase must have succeeded. To retry tasks that have used up their attempts, add --retry-failed.

Anonymity & provenance

Models only ever see anonymous inputs inside a throwaway workspace. The mapping from artifact to framework and model exists only in the ledger.

How blindness is protected

Random IDs

R-, V-, A- and S- plus 8 random hex characters. Task creation order, execution order and input order are all shuffled.

Prompt rules

Agents must not name themselves, their tools, connectors, MCP servers or environment, and must not guess who wrote what.

Redaction

Phrases like "As Claude…", "generated by Gemini…" or "Codex CLI sandbox" are replaced with [identity redacted]. Tooling residue such as chat citation tokens (citeturn0search3, 【4†source】) and utm_source= URL parameters is removed. Each redaction is logged in the ledger.

Fixed formats

Every phase requires the same section headings, so models' styles are harder to tell apart.
Known limits: writing style can still give a model away, and an agent with shell access could go looking around your filesystem. For stricter separation, set ledger_dir to a path outside the repo.

What the ledger records per session

Identityagent name, framework, framework version (<cli> --version), model, model source (cli-output / explicit / cli-config), every model used, effort
Timingcreated, started and finished times (UTC), duration, attempts
Executioncommand line (prompt removed), exit code, session or thread ID, token and cost usage, error, raw log path
Lineageartifact ID, subject (the report a review is about), input artifact IDs
Anonymitythe redactions applied to the output
Importsframework = external, your label as the model (source import), source path, sha256, --no-review if given; the unredacted original in ledger/logs/<run>/<R>.original.md

Files

Intake creates a dedicated runs/<run-id>/ directory for each question. Imports and phase outputs accumulate there as work progresses. Open its INDEX.md to browse the available artifacts.
